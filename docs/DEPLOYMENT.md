## Устройство сервера

| Путь | Назначение |
| --- | --- |
| `/srv/muse/releases/<SHA>-<UTC-время>` | Код отдельной версии с production-зависимостями |
| `/srv/muse/current` | Символическая ссылка на активную версию |
| `/srv/muse/previous` | Предыдущая успешная версия для отката кода |
| `/srv/muse/incoming` | Передаваемые архивы релизов |
| `/srv/muse/shared/.env.local` | Секреты production, права 0600 |
| `/srv/muse/shared/uploads` | Постоянные вложения вне публичного каталога |
| `/srv/muse/shared/sessions`, `log` | Сессии PHP и журналы приложения |
| `/srv/muse/maintenance` | Флаг ответа 503 на время согласованного бэкапа и переключения |
| `/var/backups/muse/<UTC-время>-<PID>` | Согласованные копии БД, вложений и настроек |
| `/usr/local/sbin/muse-ops` | Проверенный root-owned скрипт ограниченных операций |

PostgreSQL слушает только `127.0.0.1`; БД и роль называются `muse`. Пароль БД и APP_SECRET сгенерированы на сервере, в репозитории их нет. PHP работает от `muse`, максимум два процесса по 128 МБ; PostgreSQL настроен на 20 соединений и 128 МБ shared_buffers. Nginx отдаёт только `public`, выполнение произвольных PHP-файлов запрещено. Лимиты загрузки согласованы с приложением: 50 МБ на файл, до 260 МБ на HTTP-запрос.

Код собирается в GitHub Actions. Сервер не устанавливает Composer-зависимости при обновлениях. `deploy/build.sh` берёт файлы конкретного Git-коммита по явному списку, устанавливает зависимости без dev и записывает SHA в `REVISION`; `var`, тесты и локальные секреты в архив не входят.

## Первичная установка

Конфигурация сервера хранится в `deploy/`. `bootstrap.sh` предназначен для отдельного чистого сервера Ubuntu 24.04, требует root и устанавливает пакеты, создаёт роль/БД и каталоги, настраивает Nginx/PHP/PostgreSQL, операции и таймеры. При повторе существующие секреты сохраняются; существующий nginx-vhost не перезаписывается, чтобы сохранить будущую настройку TLS. Изменения действующего vhost нужно применять отдельно после проверки.

```bash
scp -r deploy root@155.212.164.198:/root/muse-deploy-setup
ssh root@155.212.164.198 'bash /root/muse-deploy-setup/bootstrap.sh'
```

Команда копирования выше рассчитана на отсутствующий каталог назначения. При повторной передаче копируйте **содержимое** `deploy/` в существующий каталог, чтобы не получить вложенный `deploy/deploy`.

Пакеты PostgreSQL 17 установлены по [инструкции PGDG для Ubuntu](https://www.postgresql.org/download/linux/ubuntu/). Общий порядок Composer, кеша и миграций соответствует [рекомендациям Symfony](https://symfony.com/doc/7.4/deployment.html).

## GitHub и обычный выпуск

Настроено environment `production`, доступное только защищённым веткам. В нём находятся:

| Настройка | Тип | Значение/назначение |
| --- | --- | --- |
| `DEPLOY_HOST` | Variable | `155.212.164.198` |
| `DEPLOY_URL` | Variable | `http://155.212.164.198`; после HTTPS заменить на `https://musetracker.ru` |
| `DEPLOY_SSH_KEY` | Secret | Отдельный приватный ключ пользователя muse |
| `DEPLOY_KNOWN_HOSTS` | Secret | Проверенный host key сервера; StrictHostKeyChecking включён |

Публичный ключ установлен в `/home/muse/.ssh/authorized_keys` с ограничением `restrict` (без перенаправлений портов и PTY). Пользователю `muse` разрешён sudo только для `/usr/local/sbin/muse-ops`. Скрипт принимает фиксированные операции и проверяет SHA; PHP-код и распаковка запускаются от `muse`, не от root.

1. Внести изменение в короткой ветке, открыть PR и дождаться CI.
2. Выполнить squash merge в `main`.
3. GitHub → Actions → **Deploy production** → Run workflow → выбрать `main`.
4. Workflow повторно проверит выбранный коммит на PHP 8.2/8.3/8.4 с чистыми PostgreSQL, соберёт архив на PHP 8.3 и передаст его по SSH.
5. Сервер прогреет кеш новой версии, включит 503 и остановит PHP, чтобы дождаться завершения запросов; затем сделает бэкап, применит миграции, проверит схему/соединение БД и переключит `current`.
6. PHP запустится, проверка `/login` выполнится на сервере и извне. Результат, SHA и путь бэкапа видны в Actions.

Деплой с других веток не выполняется. Параллельные деплои сериализованы в GitHub и через `flock` на сервере. Регистрация и прочие правила MVP этим этапом не меняются. Пользователь создаёт аккаунт самостоятельно через интерфейс; пароль не передаётся агенту.

## Ошибки и откат

До переключения ссылки активной остаётся предыдущая версия. Если проверка после переключения не проходит, скрипт возвращает предыдущую ссылку. Если не удаётся запустить PHP или первый релиз завершился ошибкой и предыдущего нет, сохраняется режим обслуживания. Действующая БД автоматически назад не мигрируется.

Оператор может вернуть предыдущую сохранённую версию кода:

```bash
sudo /usr/local/sbin/muse-ops rollback
```

Перед ручным откатом убедитесь, что предыдущий код совместим с текущей схемой. Для несовместимых миграций требуется отдельный план восстановления БД и вложений. Старые релизы автоматически не удаляются: следите за диском; при очистке сохраняйте активную и предыдущую версии. Входящие архивы удаляются после успешной активации.

## Резервное копирование и восстановление

`muse-backup.timer` запускается ежедневно в **00:30 МСК**. На время копирования PHP останавливается и новые запросы получают 503: это обеспечивает согласованность `pg_dump` и вложений. В каждом каталоге копии находятся `database.dump`, `shared.tar.gz` (вложения и .env.local), `release.txt`, `SHA256SUMS` и маркер `COMPLETE`. Локально копии хранятся 7 дней. Бэкап также создаётся перед каждым деплоем и откатом.

FirstVDS уже настроил `autobackup.timer` на **01:09 МСК**. Исходный список путей содержал `/var/www`, `/etc`, `/home`; в `/opt/autobackup/config.yml` добавляется `/var/backups/muse`, чтобы готовые дампы и файлы копировались во внешнее хранилище. Исходная конфигурация сохраняется на сервере как `/root/autobackup-config.before-muse.yml`. Секреты провайдера не выводятся и не включаются в Git. Это дополняет [автобэкап FirstVDS](https://firstvds.ru/services/autobackup), который без панели по умолчанию не копирует БД.

```bash
sudo /usr/local/sbin/muse-ops backup
sudo systemctl status muse-backup.timer autobackup.timer
sudo systemctl show muse-backup.service autobackup.service -p Result -p ExecMainStatus
```

Для проверки восстановления используйте отдельную временную БД. Проверьте `sha256sum -c SHA256SUMS` и наличие `COMPLETE`, восстановите дамп через `pg_restore --exit-on-error`, сравните таблицы и количество строк. Проверьте состав `shared.tar.gz`. Рабочую БД ради проверки не заменять.

При настоящем восстановлении: остановить запросы/PHP, сохранить текущее состояние, вернуть БД и вложения **из одного каталога копии**, восстановить секреты при необходимости, выставить владельца `muse` и права, вернуть совместимую версию кода, запустить PHP и проверить вход/задачи/вложения. Путь и время внешней копии выбираются в панели FirstVDS; наличие сервиса само по себе не подтверждает успешную внешнюю копию — проверяйте результат задания.

## Обслуживание

- `muse-cleanup.timer` ежечасно обрабатывает очередь удаления файлов через `app:files:cleanup`.
- Логи PHP/приложения ротируются; контролировать `df -h /`, `free -m`, `journalctl -u php8.3-fpm`, `/var/log/nginx/error.log`.
- Обновления системных пакетов и смена major-версии PostgreSQL — отдельные операции. Сохранены существующие unattended-upgrades и firewall FirstVDS.
- Изменения `deploy/muse-ops`, PHP/Nginx/systemd-конфигураций после PR устанавливаются администратором: обычный деплой приложения не заменяет root-owned файлы автоматически.
